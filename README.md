# Cross-Layer Characterization Framework for HPC System Utilization

Artifact for the IEEE Cluster 2026 paper *"Cross-Layer Characterization
Framework for HPC System Utilization"* (Hari Teja Jajula, Purushotham V.
Bangalore, University of Alabama).

The framework joins three facility telemetry sources that are normally analyzed
in isolation — **scheduler** metadata, **GPU** telemetry (DCGM), and
**Darshan** I/O profiles — into a single **row-per-job feature matrix**, then
uses that matrix to (1) assign each job a deterministic workload-taxonomy tier
and (2) predict, at submission time, whether an allocation is likely to
under-utilize its resources. Evaluated on a 13-month, 262,634-job public
ALCF Polaris corpus.

> The correlation/join across layers is the contribution. The individual
> telemetry streams already exist at facilities; this tool aligns them at job
> granularity and turns them into diagnostic and predictive artifacts.

## Getting the data

This repository contains **code and result artifacts only**. The raw telemetry
is public but large (tens of GB) and is downloaded separately. See
[`DATA_ACCESS.md`](DATA_ACCESS.md) for exact instructions. In short:

| Layer | Source |
|---|---|
| GPU telemetry (`POLARIS_GPU_NODE`) | ALCF public reports: <https://reports.alcf.anl.gov/data/polaris.html> |
| Scheduler job records (`DIM_JOB_COMPOSITE`) | ALCF public reports (same page) |
| Darshan I/O logs (Polaris) | ALCF Polaris Darshan log collection — Snyder et al., **CUG'25** (DOI [10.1145/3757348](https://doi.org/10.1145/3757348)); follow that paper's collection/anonymization workflow |


## Pipeline

Set your local paths in `config/config.json`, then run the stages in order.
The full orchestration is in `scripts/run_full_pipeline.sh`; individual stages:

```bash
python -m pipeline.stage00_validate               --config config/config.json   # pre-flight checks
python -m pipeline.stage00_convert_gpu_to_parquet --config config/config.json   # one-time: GPU csv.gz → date-partitioned Parquet
python -m pipeline.stage01_parse_gpu              --config config/config.json   # GPU telemetry → per-job slice
python -m pipeline.stage02_parse_darshan          --config config/config.json   # Darshan logs → per-job I/O summary (longest step)
python -m pipeline.stage03_build_combined         --config config/config.json   # join all layers → combined_metrics.csv
python -m pipeline.stage00_consistency            --config config/config.json   # 10-section consistency/leakage audit
python -m pipeline.stage07_paper_stats            --config config/config.json   # taxonomy + all headline tables
python -m pipeline.stage10_predictive             --config config/config.json   # M0–M5 submission-time prediction
```

Stages `04`–`06`, `08`, `09`, `11` produce fingerprints, repeatability scores,
HTML/text reports, per-user forensics, a security audit, and example job
reports. `stage07_paper_stats.py` reproduces the paper's Tables 1–4 and the headline
numbers in `run_artifacts/probe_52665894.out`.

## Reproducing the headline numbers

`run_artifacts/probe_52665894.out` is the authoritative production run. Its
numbers (262,634 jobs; 16.53M allocated GPU-hours; DCGM 78.1% / Darshan 25.2% /
joint 18.4% coverage; 60.2% under-utilized GPU-hours; Failed_Job 42.1%;
ρ(GPU_util, io_time_frac) = −0.411; M5 AUC 0.894) are regenerated by
`pipeline/stage07_paper_stats.py` and `pipeline/stage10_predictive.py`. Every number was
re-verified against the feature matrix for camera-ready — see
[`docs/NUMBER_AUDIT.md`](docs/NUMBER_AUDIT.md).

## Environment

```bash
pip install pandas pyarrow numpy scikit-learn pydarshan
# darshan-parser (from the Darshan tools) is needed for stages 05/08
```

The production runs used Python 3.11 on a CPU node. Some stage scripts still
contain absolute run-time paths from the original environment
(`/pscratch/sd/h/hjajula/...`); point `config/config.json` at your own data and
override the few hardcoded constants noted in `docs/REPRODUCIBILITY.md`.
